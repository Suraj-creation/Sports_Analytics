# Identity review ledger (internal building block)

`IdentityReviewLedger` records an explicit human review associating a session player with a participant observation for an inclusive frame interval. It is not connected to the API, UI, shot attribution, match scoring, movement analytics, or team inference. It does not identify players automatically and does not change existing analytics. Do not present it as a usable player review feature.

The caller supplies the session's valid player IDs, analyzed frame limit, and canonical frame rate. The ledger accepts only a participant first-observed or entered event from `participant_tracker_v1`, rejects intervals extending before that event, past the analyzed limit, into a known exit, reused track ID, or another tracker epoch, and rejects overlapping mappings for the same player, participant, or epoch-scoped track. A successful review is a human-verified event citing the observation; revocation appends a retraction. The latest live event view survives reopening the event store. A reviewer must inspect visual evidence for the entire interval: these checks do not establish identity or prove visibility throughout it. Re-identification suggestions and provisional team associations never become verified identities through this ledger.

Review records are deliberately excluded from the engine's frame-based correction carry-over during reanalysis: the same frame or numeric track can refer to a different detection in a new run. Reviews must be re-established against the new analysis. Session backups remain necessary before reanalysis.

Future integration must serialize validation and writes on the session runner, authenticate the reviewer, require an explicit confirmation, expose errors and persisted result IDs, and publish new events. The existing command bus supplies transient replies without request correlation or a durable synchronous result; ordinary corrections return HTTP 202 before runner validation. A reliable request/result protocol is needed before exposing this write path. The ledger's check and append are not atomic across independent writers, so do not call it concurrently from API and worker processes. Identity mapping alone is insufficient for doubles shot attribution; participant-scoped temporal observation and confidence evidence are separate requirements.

## Integration design still required

An authenticated review write must enter a durable request journal outside `events.sqlite`, since `reset_analysis()` replaces that file and runner shutdown can discard queued in-memory work. Give every request an opaque correlation ID, record the authenticated caller and operation, bind it to the current analysis generation, and return HTTP 202 only as **queued**, never as success. A session-scoped status endpoint should report `queued`, `running`, `succeeded`, `rejected`, or `stale`, including the durable event ID on success and a safe error on rejection. The existing auth is single-user; a session participant is not a user account.

On runner startup, recover requests left queued or interrupted. The runner must validate the current session player list and generation immediately before applying a request, and serialize all ledger writes. Record the request ID in the same atomic event-log append as the review or revocation. After a crash between event append and journal update, recovery must find that ID and finalize the same outcome, never append another review or assert failure without reconciliation. Reanalysis must atomically advance the generation before accepting work against the replacement event log, mark pending older requests stale, and make historical successes clearly refer to the old generation; do not transfer review identity by frame. If the old log was already replaced and an interrupted operation's result cannot be reconciled, report an explicit indeterminate/stale result, not success or automatic retry against new observations.

The current catalogue and per-session event log have separate SQLite connections and no cross-database transaction; the command bus has transient uncorrelated replies and no acknowledged delivery. This design is not implemented. A future implementation needs tests for concurrent reviews, command redelivery, crashes on either side of append, stopped-runner restart, queue loss, reset races, stale generations and authenticated rejection before providing an API.

A concrete approach is a separate durable SQLite journal under the data directory, with a unique request ID, session ID, analysis generation, request body, authenticated reviewer, status, result event ID and timestamps. The journal provides atomic compare-and-set transitions and a session-generation row with an `active`/`resetting` gate. The API transaction creates a request only while that row is active, then signals the runner; a lost signal is recovered by scanning journal rows after restart, so the bus is a wake-up mechanism rather than the source of truth. The API returns the request ID and `queued`; status reads use the journal and distinguish rejection, stale generation and indeterminate recovery from success.

Avoid a cross-database atomicity claim: generate a unique stable result event ID from the request ID, include that request ID and generation in the event itself, and make event append idempotent by its primary key. The one session runner reads the journal, validates the current session players and episode, and appends the review/retraction to the current event log before recording success in the journal. If the process dies after append but before journal finalization, recovery first searches for that exact event ID and validates the request ID, generation and operation before recording success; if absent in the same still-active generation it retries validation and append. Unknown or conflicting evidence is rejected or left indeterminate, never silently promoted. Future ledger confirm/revoke APIs need explicit idempotency keys and stable event IDs before this is possible.

Reanalysis must first atomically close the journal's generation gate, prevent new requests, stop and join the runner, and resolve or mark pending old-generation requests stale. Only then may it back up/reset the event store and advance the generation. During any interrupted reset the gate stays closed until recovery has determined which event log and backup exist; it must not resume an old request against new observations. Old completed results retain their generation and are explicitly historical once the active generation changes. This state machine needs cross-process tests against the Redis-backed deployment as well as local mode; ordinary in-process locks do not protect separate API and engine processes.

Generic verification now rejects `identity_review`, `identity_ambiguity`, `participant_observation`, and `doubles_team_hypothesis` at the API boundary and again in the session worker. These epoch-scoped events are excluded from frame-based reanalysis carry-over. This prevents a generic payload edit or a similarly timed old event from overwriting the evidence for a tracker reset; it does not create a reviewed-identity user interface.
