## Executed data path and authority

The application probes source media, plans and transcodes a CFR proxy, decodes committed HLS fragments, calls `BadmintonSession.perceive` serially, ingests contiguous `ChunkPerception` into `BadmintonEngine`, then persists derived tracks/events and projects them into API/UI results. Source-video keyframes initialize calibration and the TrackNet background; that warm start is separate from the canonical proxy decoder.

Within perception, each chunk runs histogram cut detection and court/camera classification; derives main/alternate/absent view and calibration state; runs TrackNet windows grouped by camera shot with target-court flight masks; runs scheduled person detection, tracking and pose; optionally associates short-lived neural appearance identities and observes racket geometry; then samples scoreboard OCR outside chunks that began in play. The engine stabilizes pixels into the calibration reference, computes valid floor coordinates for feet, separates temporal segments, filters/interpolates shuttle tracks with provenance, proposes contacts/rallies/strokes, reconciles outcomes and scores, and emits events.

Model output is evidence. Tracker boxes, interpolated shuttle points, participant identities, contact estimates, rule stroke scores and eventual score decisions are different products with different authority. A visually observed ellipse near a shuttle is not confirmed racket impact. A floor homography is not an airborne 3D reconstruction.

## Boundaries that are implemented, and those that remain open

### Coordinates and time

1. Decoded pixels are BGR at proxy resolution. Detector/pose/shuttle preprocessing uses model-specific RGB/size/normalization, then outputs proxy pixel coordinates.
2. Camera tracking describes `G_t: reference pixels → current pixels`. Engine uses its inverse to stabilize observations; `H: floor metres → reference pixels` maps ground contact points only. Court or camera validity gates foot projections.
3. Racket ellipse geometry has an explicit image-space transform. A transformed ellipse/pose/shuttle remains image evidence, not an observed contact or 3D trajectory.
4. Model windows, event frames and UI time use the CFR proxy. Source sampling time is separate, and source timestamps and duplicate/drop history are not retained per analysed frame.
5. Camera shot ID is a cut epoch, not sport stroke, named camera identity, participant identity or source replay identity.

### Singles, doubles and multi-court

The player path supports two singles slots or four doubles players plus bounded transient candidates. It preserves unresolved visual identity and participant episodes. Doubles has explicit attribution limitations and cannot inherit the singles BST assumption. Current raw/canonical visual IDs are not player names or team membership; review and assignment remain distinct.

Court isolation is implemented as geometry-gated candidate exclusion, selected court lock and masked heatmap extraction. Its documented “outside court”/neighbour exclusion metrics do not establish shuttle detection recall, hit correctness or point accuracy. Same-camera spectators, overlapping near-boundary participants, occlusion and high shuttle flight remain evaluation cases. No target-clip labelled four-player identity evaluation was performed here.

### Configured but unavailable/disconnected behavior

`BadmintonSession.capabilities` is the best current runtime declaration: requested, loaded, unavailable, fallback, disabled and unsupported are separate. Actual stages are TrackNet, RF-DETR or YOLOX, RTMPose, optional OSNet in doubles, RapidOCR, optional classical racket geometry and rule contact/stroke algorithms. Model choice alone does not prove availability.

`shuttle_live`, `shuttle_second_opinion` and requested InpaintNet explicitly report unsupported. BST is an explicit singles shadow evaluator. No trained racket detector, monocular 3D shuttle trajectory, independent replay-content recognizer, authoritative airborne floor projection or automatic court-boundary line judge is executed. TorchCodec GPU decoding is not connected. ONNX/TensorRT availability must be reported from actual runtime/provider metadata and verified artifacts, not inferred from an enum or registry entry.

Configuration is defined by `engine/src/bai_engine/config.py:{ModelChoice,Rates,Profile,Settings}` and `config/profiles/{cpu-dev,gpu-rtx4000,gpu-high,gpu-doubles-identity}.yaml`. Model names resolve through `models/manifest.yaml`; reported stage references use the registry version and actual runtime/provider data. The inspected versions are TrackNet `3.0`, RF-DETR `1.4.2`, RTMPose `1.0`, OSNet `1`, geometric racket `1`, contact fusion `2` and rule strokes `0`. RapidOCR's `rapidocr_v4` alias does not prove OCR generation/version: `ScoreboardReader.model_ref` records actual package version and loaded stage-weight digests.

The CPU profile requests TrackNet FP32/Torch, RF-DETR nano/384, RTMPose body7/192×256, detection and pose stride 3 in play / 15 idle and OCR every two seconds. The RTX profile requests TrackNet FP16/Torch with four-window batches and stride eight, RF-DETR small/512, RTMPose body7/192×256, detector stride 2/6, pose stride 1/6 and OCR every second. GPU profiles set OSNet retention to eight seconds; the associator class default is one second. Requested profiles are not evidence of the active server profile or model availability.

The `rtmpose_x_halpe26` name is misleading: its manifest source is a 384×288 body7 export, with an explicit note that the heel/toe export remains future work. The current consumer contract is 17 COCO keypoints. The high profile must not be described as delivering 26-keypoint foot reconstruction. Profile `chunk_frames=64` is not the HLS segment-frame contract, and profile `analysis_height` does not drive `Settings.proxy_height`. The unused cadence/refinement knobs in PT-07 do not alter current execution; current model overlap `shuttle.params.step`, person/pose cadence and OCR cadence do have call-site consumers.
