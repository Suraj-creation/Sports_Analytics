## Partial, missing and disconnected behavior

- `api.control` exposes start/stop, but production UI uses reanalyse only; startup on upload and explicit retry are the current user flow. `api.verifyEvent` has no production caller found. Generic verification exists as an API capability, not a surfaced review workflow. Specific winner/official/match-start and participant review actions are connected.
- Router validation still accepts legacy `highlights`, `stats`, `heatmaps` and `events` tab names while SessionWorkspace's visible tabs use moments/head-to-head/court and no event tab. These values fall through to overview rather than preserving older deep-link intent; add an alias mapping or reject them deliberately.
- Four-player individual review is connected through Visual track observations; the two P1/P2 statistics selectors and product people-history grouping are a different, legacy scoring-slot view. Global capabilities and the quality-panel “Two court-side identities” description do not fully express the distinction between reviewed four-person analytics and unverified automatic tracking.
- No speed/3D shuttle metric, independent athlete identity, challenge completion, background notifications or model accuracy evaluation is implemented by these frontend projections. Capability flags/copy generally acknowledge this. Do not count generated prototype screens as implementation evidence.
- The Event log export promises complete evidence/corrections while its plain link downloads only effective events. Full lineage is available through `?live=false`; no complete-history UI choice was found.
- Download anchors do not expose server-side export errors within the current page. Ask provider-status errors are not separately displayed, though answer request failures are. These are user feedback gaps, not evidence that the underlying feature is absent.
- Queued score/event corrections have no command-specific durable completion/failure subscription. A normal successful browser correction proves the happy path only; rejected worker commands need a receipt/error contract and corresponding browser assertions (FA-09).

### Repeated evidence cue browser investigation

The production browser test initially reported that replaying frames 90–105 never became unpaused. Read-only tracing of `VideoStage.tsx`, `clip.ts`, `stores/playback.ts`, `frameClock.ts` and SessionWorkspace found that each cue creates a fresh clip, seeks the canonical start and invokes playback; boundary enforcement uses current media time. The integration owner's browser event trace then recorded `play`/`playing` for all three cues followed by a pause at frame 105 about 500 ms later. Remote CDP polling missed that brief unpaused window. This is a **test timing failure, not a reproduced application replay defect**. The integration owner changed only the E2E assertion to install the browser's playing-event observer before dispatching the cue. No playback production change or new unit test was made for this investigation. The final full browser rerun passed all eight checks in 2.6 minutes.
