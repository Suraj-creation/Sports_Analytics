## Concrete migration and behavior

The existing `BAI_LLM_BUDGET_TOKENS_PER_SESSION` keeps its 400,000 default and gains a nonnegative constraint. New `BAI_LLM_BUDGET_MODE` defaults to `reported`. New `BAI_LLM_MAX_OUTPUT_TOKENS_PER_CALL` defaults to None; leave it unset to preserve adapter defaults: Anthropic 16,000 and OpenAI-compatible 4,096. Explicit positive overrides are supported. No model, profile or weights change.

Reported mode preserves configured native providers. It reserves a requested output envelope before **each** generation/repair call and permits one unknown-input in-flight call per session. It settles complete provider-reported total tokens immediately, including all disjoint Anthropic input/cache/output categories or OpenAI's prompt-plus-completion total. OpenAI cached/write details are subsets and are not added a second time. The counter can cross its limit on one response because input tokens were not known before dispatch. It then refuses later calls. This is prospective reported-usage admission, **not a pre-dispatch total-token or currency billing hard cap**. [OpenAI usage reference](https://developers.openai.com/api/reference/resources/chat/subresources/completions/streaming-events), [Anthropic cache usage semantics](https://platform.claude.com/docs/en/build-with-claude/prompt-caching).

Unknown/missing/inconsistent usage or an exception after dispatch is never treated as zero. Reported mode keeps the durable pending output reservation, records known components, marks uncertainty and refuses future model calls. It does not automatically retry, refund, expire a lease or delete uncertainty. Deterministic summaries remain available. Current native SDK constructors explicitly use zero automatic transport retries and a 30-second I/O timeout. That is not a process-wide wall-clock deadline or proof about provider-internal routing.

Strict mode is an explicit opt-in. It requires a typed provider capability attesting a conservative upper bound for the exact full request, no automatic retries and an enforced output cap. It reserves the input bound plus requested output before dispatch. Current native adapters do not attest this contract; `/ask/provider` reports strict unavailability and calls fall back deterministically. No character estimate or different counting endpoint is silently substituted. Independent providers remain injectable and can expose the explicit capability; a declared contract still requires backend validation.

The dedicated `data/llm_budget/<session_id>.sqlite` reuses the existing EventStore schema/public transaction/meta APIs; existing analysis databases need no schema migration. Its short `BEGIN IMMEDIATE` transactions serialize independent connections/processes. No DB or repository lock spans counting or generation. The ledger outlives analysis reset/restore, and its scope explicitly says `from_ledger_creation;prior_usage_unknown`. It cannot reconstruct earlier unmetered usage. Backups/retention must include this new directory; deleting/resetting the analysis must never replenish it. Uncertain accounting needs explicit review/reconciliation; no unsafe reset/refund endpoint is supplied.

Every successful turn settles before the loop proceeds. Earlier successful usage remains counted when a later turn fails or a stale answer is withheld by the existing event-sequence fence. The API keeps its answer/citation behavior and adds policy/strict-capability disclosure to provider information. Configured provider availability and per-call admission remain distinct.

## Retention, deletion and restore migration

Budget files deliberately live outside `sessions/<id>/events.sqlite` so reset/reanalysis and restoration of an older sporting ledger cannot replenish the model allowance. The existing session-delete operation does not remove `data/llm_budget/<session_id>.sqlite`; this is intentional retained accounting evidence, not another live sporting session. Include this directory in application backups and restoration plans. Disk retention/pruning requires an explicit documented policy; do not delete a ledger to clear an exhausted/uncertain allowance. There is no automatic expiration, unsafe refund/clear endpoint or currency reconciliation service in this change.

Existing sessions begin prospective accounting at first ledger creation. Earlier LLM usage cannot be reconstructed from current event logs or aggregate metrics, and the ledger labels that prior usage unknown. Reported-mode admission can overshoot the configured total on one response because input size was not bounded in advance. Native strict admission remains unavailable until a backend supplies a verified exact-request input upper bound and enforceable completion/retry contract. These are explicit limits; no historical or universal billing hard-cap claim is made.

## Transport, fallback and admission limits

The native SDK client constructors explicitly set `max_retries=0` and 30-second I/O timeouts. This disables automatic **client transport** retry. Anthropic's existing server-side fallback option remains unchanged; this patch does not attest that a single HTTP request causes only one server-internal generation or route, nor does it disable provider safety/refusal behavior. The timeout is an SDK I/O limit, not a process-wide wall-clock deadline or guaranteed cancellation of work already accepted by a provider.

Reported mode serializes each session's unknown-input in-flight generation. With consistent configured limits across API workers, one completed response can push the reported total beyond the configured limit because prompt size was not bounded before dispatch. The ledger then withholds later calls; missing/uncertain usage blocks admission immediately without an invented zero. This bounds subsequent application admission, not total billed tokens, vendor-internal work, account-wide dollars or a remote provider's honesty. Each explicit retry needs another admissible request; uncertain reported attempts cannot be retried automatically.

Strict mode remains an explicit provider contract and unsupported by current native adapters. The provider-information endpoint discloses the selected mode, configured limit, adapter/default output cap, strict capability and per-call admission scope. Default reported mode keeps configured native providers available. The unchanged adapter defaults 16,000/4,096 are retained when the override is unset.

The dedicated ledger begins prospective metering on creation. Earlier unmetered calls remain unknown and cannot be recovered from sporting event logs; no historical session-wide hard-cap claim follows. Retention, deletion, backups and restore must preserve this separate accounting directory. No clear/refund endpoint or automatic lease expiration is provided.
